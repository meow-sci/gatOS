The gatOS [Model Context Protocol](https://modelcontextprotocol.io/) server is the first-class
interface for an AI agent operating Kitten Space Agency. It reads the same live telemetry snapshots
and sends the same game-thread commands as `/sim`, HTTP, MQTT, and serial — but it is designed around
the questions an agent actually asks.

That means JSON documents for a world, a celestial body, a vessel, a kitten, or a runtime feature;
and logical tools such as `gatos.ignite_engines`, `gatos.vessel_control`, `gatos.execute_batch`, and `gatos.schedule_batch`.
It is deliberately **not** a one-tool-per-`/sim`-file mirror. The filesystem is still the best way
for a human to explore the game from a terminal.

:::note[The complete contract]

This page is an orientation. The complete, versioned resource URI and tool-schema contract lives in
[SPEC_MCP.md](https://github.com/meow-sci/gatOS/blob/main/SPEC_MCP.md).

:::

## Connect locally

MCP uses Streamable HTTP at `http://127.0.0.1:4243/mcp` by default. It binds only to loopback,
falls back to an ephemeral port if the preferred port is occupied, and accepts no bearer token. The
server validates exact local `Host` and `Origin` values; the gatOS status window reports the actual
bound port. Configure it with `mcp_enabled` and `mcp_preferred_port` in `gatos.toml`.

## Start with capabilities

Call `gatos.get_capabilities` first. It tells an agent which optional systems are live (camera,
schedules, audio, debug/IVA, and render FX), the configured domain limits, authority state, and any
degraded game accessors. It is the right response to uncertainty; do not probe a disabled feature by
guessing a write.

Then use the logical read tools:

| Need | MCP operation |
|---|---|
| A current world summary | `gatos.get_world` or `gatos://world` |
| A celestial body | `gatos.get_celestial` or `gatos://celestials/{id}` |
| A vessel's flight state and fitted systems | `gatos.get_vessel` or `gatos://vessels/{id}` |
| Only EVA kittens | `gatos.list_kittens` / `gatos.get_kitten` |
| Camera, audio, schedule, or debug runtime state | `gatos.get_runtime_state` or `gatos://runtime/{feature}` |

Pass `detail:"full"` to `gatos.get_world` when the complete current snapshot is needed. List tools
return 50 items by default and accept at most 1,000 at a time. Follow `next_cursor` for the rest.
MCP does not silently trim JSON response documents: full-world and full-vessel reads are complete.
Each result includes `snapshot_sequence` and `ut` so an agent can tell whether the state it planned
from is current. Requests are capped at 24 MiB for HTTP framing safety; audio/track uploads support
chunking and should stay well below that size.

## Control with intent

Use the small, explicit verbs when that is the whole intent:

```text
gatos.ignite_engines({ vessel_id: "Hunter" })
gatos.shutdown_engines({ vessel_id: "Hunter" })
gatos.activate_stage({ vessel_id: "Hunter" })
```

Use `gatos.vessel_control` with `{ operation, vessel_id, ... }` for one flight-control action —
throttle, RCS, attitude, burns, and the vessel render controls — and `gatos.module_control` with
`{ operation, vessel_id, ordinal, ... }` for one fitted engine, RCS controller, light, animation,
docking port, or decoupler. `gatos.camera_control`, `gatos.camera_track`, `gatos.audio_control`,
`gatos.audio_clip`, `gatos.schedule_control`, `gatos.debug_control`, and `gatos.render_fx_control`
group the rest of gatOS's current game features without making an agent discover filesystem paths.

The full action coverage backstop is `gatos.command`, whose envelope is always exactly:

```json
{
  "action": "vessel.throttle",
  "vessel_id": "Hunter",
  "ordinal": -1,
  "value": 0.5,
  "values": null,
  "token": null,
  "aux": null
}
```

The action, its units, and its Frame/Solver execution phase are still the same published gatOS
semantics. MCP never lets a client choose a phase or call KSA from its request thread.

## Coordinate many commands

`gatos.execute_batch` applies up to 64 prevalidated commands as one ordered same-tick group. All members
must have the same derived phase. It is how an agent makes a formation teleport or several render
changes land together instead of once per frame.

`gatos.schedule_batch` is the JSON timed-batch counterpart. Every entry has an absolute `at_ms` offset and
a canonical command envelope; choose the existing `render`, `wall`, or `ut` clock. It returns a
schedule id immediately, then `gatos.schedule_control` or `gatos.get_runtime_state(feature:"schedules")`
can pause, scrub, rate, loop, stop, remove, or inspect it.

:::caution[Do not confuse milliseconds and seconds]

Batch schedule offsets and schedule-player positions are milliseconds. Camera-track authoring uses
seconds. The MCP tool preserves this distinction exactly.

:::

## Wait for the simulation

Avoid arbitrary sleeps. `gatos.wait` can wait for a later snapshot sequence, an event type (optionally
for one vessel), or a target universal time. Supply at least one condition; if multiple are supplied,
it returns on the first match. Its bounded `timeout_ms` returns an `ETIMEDOUT` envelope rather than
pretending paused simulation time advanced.

## Important game caveats

- Read `controllable` before ordinary flight control: KSA can silently ignore a vessel without a
  control module.
- CCI state, burns, teleport, and default impulses are about the vessel's current parent body.
- RCS translation and rotation are body-axis bang-bang commands. They are inert while RCS mode is
  disabled, and game focus/UI/large warp can clear their latches.
- Solver-phase flight-computer commands take effect on the next solver step. Same-tick batches may
  not mix them with Frame commands.
- `/sim/display` is intentionally not in MCP v1. It is an infinite Kitty terminal-video stream, not
  a logical JSON agent interface.
